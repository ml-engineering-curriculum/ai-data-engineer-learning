# mod-106 — Benchmark Contamination Detection and Decontamination Engineering

> **Role:** AI Data Engineer · **Family:** ML Engineering · **Level:** L30

**Estimated effort:** 12 hours

## What this module is about

[`mod-105`](../mod-105-deduplication-at-scale/README.md) removed duplicates on consistency and privacy grounds. This module adds the **credibility** quality control: the pipeline step that keeps benchmark test sets (MMLU, GSM8K, HumanEval, HELM scenarios, BigBench-Hard, MATH, LiveBench, LiveCodeBench, and whatever benchmarks your release claim covers) out of pretrain, SFT, preference-pair, and synthetic-data corpora — and the signed artifact that lets a reader verify the firewall held.

The deliverable at the end of the module is a single artifact — a signed `decontamination_log.yaml` — that captures, for each release:

1. **The eval manifest** — SHAs and versions of every benchmark the firewall defended against, co-signed with `model-evaluation-engineer`.
2. **The detector configuration** — n-gram width, exact-prompt matcher config, LLM-substring detector prompt SHA, normalisation rules, per-surface scope.
3. **Removal counts per benchmark, per detector, per pipeline surface** — pretrain, SFT, preference-pair, synthetic generation.
4. **Clean-subset score delta** — the GPT-3 Appendix C-style headline-vs-clean-subset gap, co-signed with `model-evaluation-engineer`.
5. **Pre-release audit** — pre-registered Min-K% Prob and Oren exchangeability test results, so the firewall's defence is on record *before* an external auditor runs the same tests.
6. **Three sign-offs and evidence SHAs** — firewall engineer, `model-evaluation-engineer`, `ai-risk-engineer`, Sigstore-signed.

By the end you will be able to hand a release reviewer a `decontamination_log.yaml` and have them know — within five minutes of reading it — which benchmarks are defended, how many eval-item leaks were caught per surface, and whether the release stands up to Shi 2023 Min-K% Prob and Oren 2023 exchangeability audits.

## Why this is a core quality control, not operational hygiene

Three public findings make the case:

- **GPT-3 Appendix C (Brown et al. 2020)** — the leading pretraining lab shipped a contamination analysis as a load-bearing appendix. Every subsequent open LLM release is read against that bar.
- **Shi et al. 2023 (Min-K% Prob) + Oren et al. 2023 (exchangeability test)** — two canonical post-hoc detectors can prove contamination of a black-box model using only API access. There is no technical defence once the model is released; the only defence is a pipeline-side firewall that actually worked.
- **EleutherAI LM Evaluation Harness + AllenAI Dolma** — both open-source projects publish working decontamination recipes and public logs. The practice is standardised and reproducible; not adopting it is the deviant choice.

Chapter 01 is the defence of this framing. Do not skip it.

## Learning objectives

- Author the **contamination firewall** — the pipeline step that keeps MMLU, GSM8K, HumanEval, HELM, BigBench-Hard, MATH, LiveBench, and LiveCodeBench test sets out of pretrain, SFT, and preference-pair generation corpora — using **n-gram overlap** (Chapter 03), **exact-prompt matching** (Chapter 04), and **LLM-based substring detectors** (Chapter 04).
- Defend the pipeline against the **Min-K% Prob detector** (Shi et al. 2023, *Detecting Pretraining Data from Large Language Models*, ICLR 2024) and the **Oren et al. 2023 exchangeability test** — the two canonical ways an auditor will try to prove contamination of a black-box model (Chapter 07).
- Run the **EleutherAI LM Evaluation Harness decontamination recipes** and compare to the **Dolma practice**; publish the decontamination log alongside the benchmark results so the benchmark number is defensible (Chapter 06 + Chapter 08).
- Handle the **recursive-synthetic-data contamination vector** — synthetic data generated by a model that has seen the eval set carries the contamination forward unless firewalled; coordinate with [`mod-108`](../mod-108-synthetic-data-generation-at-production-scale/README.md) on the generation-side firewall (Chapter 05).
- Hand off **benchmark construction** and **gold-eval-set design** depth to `model-evaluation-engineer` (peer, level 30); this module stays on the contamination-firewall engineering slice (Chapter 02 §"role split", Chapter 05).

## Prerequisites

- You have completed [`mod-101`](../mod-101-ai-data-governance-and-position/README.md) and internalised the ISO/IEC 25012 vocabulary. The firewall implements the *credibility* and *traceability* characteristics; the log is the artifact that proves it.
- You have completed [`mod-104`](../mod-104-data-quality-measurement-and-audit/README.md) and understand the per-slice quality report pattern. The decontamination log is the credibility-side analogue.
- You have completed [`mod-105`](../mod-105-deduplication-at-scale/README.md). The MinHash + LSH + sentence-level dedup infrastructure is directly reused by the n-gram overlap detector (Chapter 03).
- Python 3.11+ with `xxhash`, `datasets`, `pyarrow`, `pandas`, `pyyaml`, `mmh3`, `matplotlib`, `transformers`, `anthropic`. Exercise 02 additionally needs `lm-evaluation-harness` and `dolma`.
- An Anthropic API key for Exercises 04–05 (the LLM-substring detector). Any small instruct-tuned model can substitute at lower quality.
- Access to a small open HF model (≤ 3B parameters) for Exercise 03's Min-K% / Oren runs. GPU is helpful, not required.

## How to use this module

Read Chapter 01 first. It is the justification you will cite in every release review for the rest of the module, and the three-citation shape (GPT-3 Appendix C, Shi + Oren, EleutherAI + Dolma) is specifically what the role is accountable for being able to defend.

Chapter 02 pins the eval surface and — critically — the role split with `model-evaluation-engineer`. Do not skip the role-split section; the handoff pattern is enforced through the manifest-signoff gate and is a common point of release-time failure.

Chapters 03 and 04 are the detector catalogue. Pair them with Exercise 01 (n-gram + the normalisation round-trip test) and the LLM-substring parts of Exercise 04.

Chapter 05 is the placement guide. It is short but load-bearing — the SFT and synthetic surfaces have the highest per-example concentration, and most firewall under-coverage happens there.

Chapter 06 is the recipe decision. Pair with Exercise 02 — the three-way comparison (in-house, LM Eval Harness, Dolma) is where the recipe-choice justification is written.

Chapter 07 is the audit side — the chapter written to the detector, not the firewall. Pair with Exercise 03. Pre-register thresholds before you run the detector; threshold-tuning after the audit is not auditable.

Chapter 08 assembles the log. By the time you reach it, Exercises 01–04 have each contributed a block; Exercise 05 is the hour of assembly that produces the signed, auditable deliverable.
